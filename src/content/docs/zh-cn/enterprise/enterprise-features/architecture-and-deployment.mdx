Warp 的架构将**控制平面**（编排、可观测性和 LLM 推理）与**执行平面**（代理运行、代码访问和命令执行）分离。这种分离让企业团队能够灵活选择敏感工作负载的运行位置，同时保持集中管理和可见性。

利用这些信息来评估哪种部署模式符合你组织的安全、合规和运营需求。

## 系统架构概述

Warp 的云代理基础设施包含四个关键组件：

1. **触发** - 启动代理运行的方式（CI 步骤、Webhook、定时任务、Slack 提及、CLI 命令或 API/SDK 调用）。
2. **编排** - 决定运行什么并跟踪运行状态（Oz 编排器或你自己的系统）。
3. **执行** - 代理实际运行的位置（Warp 托管环境、你的基础设施或你现有的 CI/编排器）。
4. **可见性** - 团队监控和干预的方式（Oz 仪表板、会话共享、API/SDK）。

### 高层数据流

* **Warp 终端（客户端）** ↔ **Warp 后端（控制平面）** ↔ **LLM 提供商**
* Warp 后端负责任务编排、可观测性和 LLM 推理路由。
* LLM 提供商遵守**零数据保留（ZDR）**协议，不会存储或基于你的数据进行训练。
* **执行平面**是源代码访问、命令运行和构建产物生成的地方。这可以在 Warp 的基础设施上运行，也可以在你的基础设施上运行。

## Warp 托管（SaaS）

Warp 托管是默认的部署模式。代理在 Warp 管理的基础设施上运行，你的团队无需任何设置。

### 工作原理

* 代理在 Warp 托管基础设施（GCP）上的**隔离 Docker 容器**中执行。
* Oz 编排器管理代理的生命周期——配置、执行、监控和清理。
* 环境是临时的，每次运行后销毁。

### 触发方式

Warp 托管的代理可以通过以下方式触发：

* **第一方集成** - Slack、Linear 和其他连接工具
* **定时代理** - 类似 Cron 的自动化周期性工作
* **CLI** - `oz agent run-cloud` 按需云执行
* **API/SDK** - 从你自己的系统通过编程方式触发

### 适用场景

* 你需要最简单的可扩展云代理执行方式。
* 你需要并行运行大量任务，而不想构建沙箱基础设施。
* Warp 的 SOC 2 Type II 认证基础设施（含 ZDR）满足你的安全要求。

## 自托管执行

对于需要代理执行和源代码保留在自身网络边界内的组织，Warp 支持自托管执行。

:::note
自托管执行仅在 Warp 的**企业版**计划中可用。
:::

### 分离架构

自托管部署采用分离架构：

* **执行平面（客户托管）** - 源代码仓库、构建产物、Shell 命令和运行时密钥保留在你的基础设施上。请注意，在代理交互过程中，代码上下文会包含在 LLM 提示和会话记录中，这些数据通过 Warp 的服务器路由（遵守 ZDR 协议），参见[哪些数据经过 Warp 服务器](#what-transits-warps-servers)。
* **控制平面（Warp 托管）** - 任务编排、可观测性数据和 LLM 推理通过 Warp 的服务器路由，遵守零数据保留（ZDR）协议。

### 部署模式

**非托管模式** - 使用 `oz agent run` 在你的现有编排器或 CI 环境中运行代理。支持 Linux、macOS 和 Windows，无需 Docker 依赖。

* 最适合已有 CI/CD 基础设施或内部编排器的团队。
* 由你控制调度、扩展和环境设置。
* Warp 提供云连接、共享上下文、可见性和会话共享。

**托管模式** - 运行 `oz-agent-worker` 守护进程，让 Oz 平台在你的基础设施上的隔离 Docker 容器中编排代理。

* Worker 进程通过 WebSocket 连接到 Oz，自动接收任务。
* 代理在由 Worker 管理的隔离 Docker 容器中运行。
* 你获得与 Warp 托管相同的编排能力，但执行留在你的基础设施上。

### 网络要求

自托管代理仅需**出站**网络访问，无需入站网络访问。

**出站要求：**

* 出站访问 Warp 的后端服务（用于编排和可观测性）
* 托管模式还需：访问 Docker Hub 和 GitHub（用于容器镜像和仓库访问）

### 适用场景

* 合规或安全要求不允许使用 Warp 托管计算。
* 源代码和执行必须留在你的网络边界内。
* 你需要 Oz 编排和可见性，但不想将代码发送到 Warp 的基础设施。

## 混合部署

组织可以结合使用 Warp 托管和自托管执行，以平衡便利性与安全要求。

### 工作原理

* 将敏感工作负载（例如生产代码、受监管数据）路由到自托管代理。
* 将不太敏感的工作负载（例如开源工具、内部工具）路由到 Warp 托管代理。
* 两种执行模式共享相同的 Oz 仪表板、会话共享和 API/SDK 可见性。

### 示例配置

* **按敏感度** - 生产仓库在自托管代理上运行；暂存和开发环境在 Warp 托管上运行。
* **按团队** - 安全敏感团队（如基础设施、支付团队）使用自托管；其他团队使用 Warp 托管。
* **按任务类型** - 定时维护任务在 Warp 托管上运行；临时调试在自托管开发环境中运行。

## 数据流与边界

了解哪些数据保存在哪里对于安全和合规决策至关重要。

### 保留在客户基础设施上的数据（自托管）

* **源代码** - 仓库内容和版本历史
* **构建产物** - 编译输出和生成的文件
* **Shell 命令** - 终端命令及其输出
* **运行时密钥** - 环境变量和凭据
* **执行日志** - 代理运行日志和诊断信息

### 经过 Warp 服务器的数据

* **任务编排** - 调度、路由和生命周期管理
* **可观测性数据** - 运行状态、持续时间和元数据
* **LLM 推理** - 提示和响应（包含来自代理交互的代码上下文）通过 Warp 路由到已签约的 LLM 提供商，遵守 ZDR 协议
* **会话共享数据** - 会话记录，包含来自代理交互的代码上下文（当启用会话共享进行监控和协作时）

## 选择部署模式

选择部署模式时请考虑以下因素：

**Warp 托管**适合以下情况：
* 你希望代理执行零基础设施管理。
* 你的安全团队认可 SOC 2 Type II 认证且受 ZDR 覆盖的基础设施。
* 你需要最大化并行度和可扩展性。

**自托管**适合以下情况：
* 合规要求代码必须留在你的网络内。
* 你需要集成现有的 CI/CD 或基础设施工具。
* 你希望对执行环境拥有完全控制权。

**混合部署**适合以下情况：
* 不同团队或仓库有不同的安全要求。
* 你希望大部分工作享受 Warp 托管的便利，但敏感工作负载需要自托管。
